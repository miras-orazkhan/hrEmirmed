# Шаблоны, заявки и кампании: API v1

Реализовано 17 октября 2026. Это серверный модуль планирования подбора.
Реестр кандидатов и рассмотрения доступны в отдельных API ([реестр](candidate_registry.md),
[рассмотрения](candidate_applications.md)); HTML-экраны тех же потоков описаны в
[веб-интерфейсе](web_interface.md). Внешние сообщения, тесты кандидатов и оформление
найма ещё не реализованы.

## Основные правила

- Руководитель HR создаёт шаблон и отдельно утверждает его. До утверждения новую
  заявку по нему создать нельзя. Изменение шаблона создаёт новую версию и возвращает
  шаблон в черновик. Действующие заявки продолжают ссылаться на прежнюю версию.
- Руководитель подразделения создаёт заявку только для назначенного ему подразделения.
  Рекрутер определяется шаблоном. Интервьюер выбирается явно.
- Каждому шаблону соответствует одна кампания. Она создаётся при первой заявке
  со статусом `pending_approval`. Новые заявки получают статус `ready`.
- Назначенный рекрутер запускает кампанию и сохраняет проверенный поисковый запрос.
  Готовые заявки переходят в `recruiting`. Повторный запуск работающей кампании — 409.
- Заявка в работающую кампанию подключается автоматически в состоянии `recruiting`.
- Пауза одной заявки сохраняет работу других. Когда активных заявок не осталось,
  работающая кампания переходит в `paused`. Новые заявки в ней остаются `ready`
  до явного разрешения рекрутера.
- Возобновление заявки при работающей кампании возвращает её в `recruiting`;
  при приостановленной — в `ready`. Запуск кампании не снимает индивидуальную паузу
  с других заявок.
- Отмена доступна из `ready`, `recruiting`, `paused`; отменённая заявка неизменяема.
  Если у заявки есть активные рассмотрения, запрос должен явно передать
  `{"job_requisition":{"allow_next_application":true|false}}`; рассмотрения
  завершаются как `cancelled`, а указанное решение сохраняется для следующего подбора.
- Изменение условий заявки создаёт отдельную версию. Старые зарплата, график,
  интервьюер и вопросы сохраняются. Рассмотрение фиксирует последнюю версию
  условий при явной команде начала; дальнейшие изменения заявки её не подменяют.
- Количество заполненных мест не задаётся через этот API. Закрытие и восстановление
  будут доступны через события оформления. Сейчас создать оффер или закрыть место нельзя.

## Таблицы

| Таблица | Содержимое |
| --- | --- |
| `vacancy_templates` | Статус утверждения, назначенный рекрутер, создатель |
| `vacancy_template_versions` | Название, обязанности, навыки, обязательные/желательные требования, вопросы, критерии стажировки |
| `recruitment_campaigns` | Общий поиск, рекрутер, статус, поисковый запрос, кто и когда разрешил запуск |
| `job_requisitions` | Подразделение, шаблон и его фиксированная версия, кампания, рекрутер, статус, количество мест |
| `job_requisition_versions` | Версии условий, интервьюера, формата встречи, параметров стажировки и дополнительных вопросов |

Во внешних ключах `recruiter_id`, `created_by_id`, `approved_by_id`, `interviewer_id`
и `internship_supervisor_id` целевая таблица — `users`.
`mandatory_requirements` — обязательные требования; `preferred_requirements` — желательные.

У версии есть уникальный номер внутри родителя. Версии доступны только для чтения
и добавления через приложение; UPDATE/DELETE не предоставляются API. При production
настройке роли БД также не выдавать runtime-роли UPDATE/DELETE на таблицы версий.

PostgreSQL проверяет, что заявка, версия шаблона и кампания относятся к одному
шаблону, а рекрутер заявки совпадает с рекрутером кампании и шаблона.
Уникальный индекс на `recruitment_campaigns.vacancy_template_id` исключает вторую
кампанию того же шаблона. CHECK запрещает отрицательные/лишние заполненные места,
закрытие незаполненной заявки и активную кампанию без сохранённого разрешения.

Все команды выполняются транзакционно вместе с аудитом. Создание заявки сначала
блокирует шаблон, затем кампанию. Изменения заявок и запуск блокируют кампанию перед
заявкой. Это предотвращает дубли кампаний и гонки создания/паузы/запуска.

Списки имеют пагинацию по ID. Версии для списка выбираются одним запросом с
`DISTINCT ON` по родителю: история всех версий не загружается в память приложения.
Индексы поддерживают списки по подразделению/рекрутеру, поиск заявок кампании по
состоянию и выбор версии шаблона/условий.

## Разрешения

`db:seed` создаёт начальные роли `hr_manager`, `recruiter`, `department_manager`.
Повторный запуск не перезаписывает изменения ролей, сделанные администратором.
Роль `admin` сохраняет полный доступ.

| Разрешение | Действие / область |
| --- | --- |
| `read.vacancy_template` | Чтение утверждённых шаблонов; с `manage.vacancy_template` также черновиков |
| `manage.vacancy_template` | Создание шаблонов и новых версий |
| `approve.vacancy_template` | Утверждение шаблона |
| `read.job_requisition` | Заявки своего подразделения или назначенного рекрутера |
| `create.job_requisition` | Создание заявки своего подразделения |
| `update.job_requisition` | Изменение условий заявки своего подразделения |
| `manage.job_requisition` | Пауза/возобновление/отмена назначенным рекрутером |
| `read.recruitment_campaign` | Кампании назначенного рекрутера |
| `launch.recruitment_campaign` | Разрешение запуска своей кампании |
| `read.all_recruitment` | Расширяет область чтения заявок/кампаний до всей организации; не даёт права изменения |
| `conduct.interview` | Пользователь может назначаться интервьюером в своём филиале |
| `supervise.internship` | Пользователь может назначаться ответственным за стажировку в своём филиале |

Назначенный рекрутер может быть интервьюером своей заявки. Остальные интервьюеры
должны иметь `conduct.interview` и принадлежать филиалу заявки. При обязательной
стажировке ответственный по умолчанию — создатель заявки; у него должно быть
`supervise.internship`. Неактивные сотрудники не принимаются в эти назначения.

## Маршруты

Все запросы требуют `Authorization: Bearer <token>`.

| Метод | Путь | Действие |
| --- | --- | --- |
| GET, POST | `/api/v1/vacancy_templates` | Список / создание черновика |
| GET, PATCH | `/api/v1/vacancy_templates/:id` | Просмотр / новая версия |
| POST | `/api/v1/vacancy_templates/:id/approve` | Утверждение |
| GET | `/api/v1/vacancy_templates/:id/versions` | История версий |
| GET, POST | `/api/v1/job_requisitions` | Список / создание готовой заявки |
| GET, PATCH | `/api/v1/job_requisitions/:id` | Просмотр / новая версия условий |
| POST | `/api/v1/job_requisitions/:id/pause` | Пауза |
| POST | `/api/v1/job_requisitions/:id/resume` | Возобновление |
| POST | `/api/v1/job_requisitions/:id/cancel` | Отмена |
| GET | `/api/v1/job_requisitions/:id/versions` | История условий |
| GET | `/api/v1/recruitment_campaigns` | Список кампаний |
| GET | `/api/v1/recruitment_campaigns/:id` | Карточка кампании |
| POST | `/api/v1/recruitment_campaigns/:id/launch` | Разрешение запуска или возобновления |

Списки: `limit` (1–200), `cursor`; следующий курсор в `X-Next-Cursor`.
Заявки можно фильтровать по `department_id`, `recruitment_campaign_id`, `status`.
Кампании — по `status`. Фильтры не расширяют область доступа.
Очередь ожидающих запуска: `GET /api/v1/recruitment_campaigns?status=pending_approval`.
Возобновления: кампании со статусом `paused` и их заявки со статусом `ready`.

Состояние и владельцы процесса не редактируются через PATCH. Неизвестные и
системные поля отбрасываются strong parameters. Запросы изменения прав и назначения
проверяются на сервере независимо от клиента.

### Создание шаблона

```json
{
  "vacancy_template": {
    "recruiter_id": 2,
    "title": "Врач-терапевт",
    "duties": "Приём и ведение пациентов",
    "professional_skills": ["Диагностика"],
    "mandatory_requirements": ["Действующий сертификат"],
    "preferred_requirements": ["Опыт амбулаторного приёма"],
    "screening_questions": ["Какой график вам подходит?"],
    "internship_required": true,
    "internship_criteria": ["Работа с пациентом"]
  }
}
```

Затем выполнить `POST /api/v1/vacancy_templates/:id/approve`.
Ответ содержит `current_version`; её ID впоследствии фиксируется в заявке.

### Создание заявки

```json
{
  "job_requisition": {
    "department_id": 1,
    "vacancy_template_id": 1,
    "positions_count": 2,
    "work_schedule": "5/2, с 09:00 до 18:00",
    "salary_amount": "500000.00",
    "salary_currency": "KZT",
    "desired_start_on": "2026-12-01",
    "interviewer_id": 3,
    "interview_format": "onsite",
    "internship_duration": "3 смены",
    "additional_questions": ["Когда вы готовы выйти?"]
  }
}
```

`interview_format`: `onsite` или `online`. Если стажировка обязательна, её
продолжительность необходима; `internship_supervisor_id` можно передать явно.
Сумма зарплаты хранится в decimal(14,2), код валюты — три заглавные буквы.
Ответ содержит `current_version` и вычисленное `remaining_positions_count`.

### Разрешение запуска

```json
{
  "recruitment_campaign": {
    "search_query": "Терапевт, действующий сертификат, Алматы"
  }
}
```

`search_query` — проверенное рекрутером текстовое описание поиска. Это ещё не
контракт параметров API HeadHunter. Реальная выгрузка кандидатов пока не запускается.

Ошибки состояния: HTTP 409, `error: invalid_transition`, `reason` с кодом причины.
Например: `template_must_be_approved`, `campaign_already_active`,
`no_ready_requisitions`, `requisition_cannot_resume`.
Ошибка в полях — 422 с `details`; отсутствие права — 403; объект вне области
чтения — 404.

## Границы текущего этапа и открытые решения

- Черновик заявки и запрос нового шаблона через внутреннюю задачу ещё не реализованы.
  Создание сейчас требует утверждённого шаблона и всех обязательных условий.
- Уведомления о запуске представлены состоянием кампании в API. Общая система
  задач и уведомлений сотрудников будет отдельным модулем.
- Профессиональные тесты и дополнение вопросов рекрутером будут реализованы с
  модулем первичного опроса. Сейчас дополнительные вопросы меняет подразделение.
- При паузе меняется состояние заявки. Приостановка диалогов/таймеров и сообщения
  кандидатам появятся вместе с соответствующими модулями и правилами из ТЗ.
- Смена рекрутера до появления кампании разрешена. После появления кампании API
  возвращает `recruiter_transfer_requires_separate_workflow`: перенос открытых
  заявок и замещение требуют отдельного согласованного процесса.
- Формат зарплаты пока одна сумма + валюта; диапазоны, gross/net и обязательные
  поля оффера требуют согласования. Продолжительность стажировки хранится текстом,
  чтобы не закреплять неутверждённую единицу измерения.
- Количество мест можно менять в границах уже заполненных мест. Перед появлением
  офферов нужно согласовать резервирование и изменение потребности при предложениях.
- Закрытие всех заявок через оформление и возврат места после невыхода относятся
  к этапу найма; прямого действия «закрыть заявку» здесь нет.

## Проверки

Интеграционные тесты проверяют API, области доступа, сохранение версий, откат
невалидных записей, запуск/паузу/возобновление, присоединение новых заявок,
обязательную стажировку и защиту системных полей.

Два теста с отдельными соединениями PostgreSQL проверяют одновременное создание
заявок и одновременный запуск кампании. Эти тесты используют собственные записи и
удаляют их после проверки; обычные тесты работают в откатываемых транзакциях.
