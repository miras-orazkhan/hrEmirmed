# Реестр кандидатов

API `/api/v1/candidates` поддерживает список, карточку, создание и изменение. Все запросы требуют Bearer-сессию. Списки используют `limit`/`cursor` и возвращают `X-Next-Cursor`. Карточка возвращает только явно разрешённые поля кандидата, контакты и источники.

## Кандидаты

Создание: `POST /api/v1/candidates` с объектом `candidate`, содержащим `full_name`, необязательные `preferred_language`, `city`, `summary`, `contacts` и `sources`. Контакт — `{ "kind": "phone"|"email", "value": "..." }`. Источник — `{ "provider": "...", "external_id": "..." }`. `responsible_recruiter_id` можно указать только при создании; обычный пользователь может назначить только себя, администратор — активного сотрудника. При отсутствии владельца назначается автор.

`PATCH /api/v1/candidates/:id` принимает поля карточки и/или `contacts`. Если ключ `contacts` передан, набор контактов заменяется целиком; если ключ опущен, контакты сохраняются. PATCH не меняет владельца и источники. Источники задаются только при создании; устойчивая пара `(provider, external_id)` уникальна. `provider` — строчная латиница, цифры и `_`, начинается с буквы; длина не более 50. `external_id` — непустая строка до 200 символов.

Список принимает `q` длиной до 200 символов. Телефон и email ищутся по точному нормализованному совпадению; имя — по префиксу без учёта регистра. `%` и `_` в имени считаются обычными символами. Все результаты дополнительно ограничены областью доступа пользователя.

Изменять карточку может владелец по активному рассмотрению или ответственный рекрутер карточки, если активного рассмотрения нет; администратор также может изменять её. Создание требует `create.candidate`, чтение — `read.candidate`, изменение — `update.candidate`. `read.all_candidates` расширяет область чтения до организации. Назначение на этап интервью или стажировки даёт доступ только к карточкам кандидатов в соответствующих этапах; `read.organization` само по себе досье не открывает.

`db:seed` задаёт разрешения preset-ролям только при их первом создании. Повторный seed не расширяет существующие роли: новые разрешения нужно явно выдать через управление ролями, сохраняя прочие настройки администратора.

## Возможные дубли

Совпадение точного нормализованного телефона или email создаёт запись-кандидат на проверку. `GET /api/v1/candidate_duplicates` и `POST /api/v1/candidate_duplicates/:id/resolve` требуют `resolve.candidate_duplicate`. Пользователь видит дубли своих кандидатов; `manage.all_candidate_duplicates` открывает общий список. Ответ содержит ID двух карточек, статус, `requires_hr_review` и `assignee_user_id`; полный состав карточек и контакты в ответе отсутствуют. Разные владельцы требуют проверки HR, у одинакового владельца назначенным является этот рекрутер.

Разрешение принимает `status: "distinct"` или `status: "confirmed"` и необязательный `resolution_note`. Статус фиксирует решение по совпадению. Даже `confirmed` не объединяет, не удаляет и не переносит данные кандидатов: автоматическое и ручное слияние в API не реализовано.

## Причины отказа

`GET /api/v1/rejection_reasons` требует `read.candidate`. POST и PATCH `/api/v1/rejection_reasons/:id` требуют `manage.rejection_reason`; разрешены только `name` и `active`. Неактивную причину нельзя использовать для нового отказа. Изменения справочника аудируются.
