# Архитектура и база данных hr.emirmed

Дата: 17 октября 2026. Основание: `hr_emirmed_specification_v0_1.md`.

## Статус

Реализованы API входа/выхода, оргструктуры, юрлиц, пользователей, ролей и аудита,
а также реестр кандидатов и рассмотрения. Реестр включает контакты, источники,
проверку возможных дублей, причины отказа, JSON-импорт и отдельное хранение резюме;
контракты описаны в [документации API кандидатов](candidate_registry.md).
Также реализован модуль [шаблонов, заявок и кампаний](recruitment_planning_api.md):
версии, утверждение, объединение, запуск, пауза и отмена. Его документ уточняет
реализованную часть приведённого ниже плана; остальные сущности — проект.
Предложения из ТЗ не считаются утверждёнными бизнес-правилами.

Техническая основа: Rails 8.1, PostgreSQL, фоновые задачи Solid Queue.
Веб-интерфейс — серверные views + Hotwire/Turbo (см. [web_interface.md](web_interface.md));
JSON API v1 сохранён для интеграций и сценариев без браузера. Внешние каналы и ИИ
подключаются после проверки фактических возможностей и доступов организации.

## Правила именования

- Таблицы: английский `snake_case` во множественном числе, модели — в единственном.
- `id` и внешние ключи — bigint, внешние ключи называются `<entity>_id`.
- Даты календаря — `*_on`, моменты времени — `*_at`; время сохраняется в UTC.
- Денежные суммы: decimal + отдельный код валюты, без float; формат зарплаты согласовать.
- Имена людей — `full_name`, название справочника — `name`.
- `status` используется для состояния процесса; `active` — для доступности учётной записи.
- Критичные связи и поля фильтрации — отдельные колонки. JSONB — только для
  небольших структур переменной формы, без переноса всей модели в JSON.
- Названия `requests`, `applications`, `tests`, `sessions` без предметного контекста
  не используем для новых таблиц найма.

## Реализованная схема

| Таблица | Назначение и ключевые поля |
| --- | --- |
| `branches` | Филиал: `name`, `address` |
| `departments` | Подразделение: `branch_id`, `name` |
| `legal_entities` | Юрлицо оформления: `name`, `registration_number` |
| `users` | Учётная запись: `login`, `full_name`, `password_digest`, `active`, `branch_id`, `role_id` |
| `roles` | Роль: `name`, `permissions` |
| `user_departments` | Назначение сотрудника: `user_id`, `department_id`, `branch_id` |
| `auth_sessions` | Сессия входа: `user_id`, `token_digest`, `expires_at` |
| `audit_events` | Аудит: `actor_user_id`, `action`, `subject_type`, `subject_id`, `changeset`, `created_at` |

Первая миграция сохраняет историю разработки. Вторая переименовывает таблицы и
поля без удаления строк: `sessions` → `auth_sessions`, `department_memberships`
→ `user_departments`, `users.name` → `full_name`, `actor_id` → `actor_user_id`.

У пользователя сейчас одна настраиваемая роль, один филиал и несколько подразделений.
Минимум одно подразделение проверяется в модели; имена и логины имеют ограничения длины.
`roles.permissions` — небольшой JSONB-массив из фиксированного каталога. По нему
нет поиска, поэтому GIN-индекс не нужен. Расширение каталога требует миграции CHECK.
Отдельные таблицы разрешений понадобятся, если права станут самостоятельным
пользовательским справочником с дополнительными атрибутами.

`branch_id` в `user_departments` дублируется намеренно: составные внешние ключи
на `(users.id, users.branch_id)` и `(departments.id, departments.branch_id)`
запрещают связь пользователя с чужим филиалом даже при прямом SQL/импорте.
Проверка откладывается до конца транзакции, чтобы можно было одновременно
перевести пользователя и заменить назначения. Весь перевод атомарен.

Юрлица пока не привязаны к филиалам: эта связь не утверждена в ТЗ.
`registration_number` не считается уникальным идентификатором до согласования формата.
Полиморфная ссылка аудита не имеет FK на объект, чтобы событие могло пережить
удаление сессии. FK на автора сохраняет связь с учётной записью.

## Доступ

| Разрешение | Область |
| --- | --- |
| `read.organization` | Свой филиал, назначенные подразделения, справочник юрлиц |
| `manage.organization` | Создание/изменение оргструктуры и юрлиц по всей организации |
| `manage.users` | Администрирование учётных записей по всей организации |
| `manage.roles` | Администрирование ролей и набора разрешений |
| `read.audit` | Просмотр журнала организации |
| Роль `admin` | Все перечисленные действия |

Для просмотра оргструктуры управленцу также выдаётся `read.organization`.
`manage.roles` и `manage.users` — административные полномочия; не выдавать их
обычным рекрутерам. Изменять пользователей с ролью admin и назначать эту роль
может только admin. Встроенная роль admin не переименовывается через API.
Удаление справочников и пользователей через API пока отсутствует; пользователя
можно деактивировать. Права проверяются заново на каждом запросе.

Права на кандидатов разделяют чтение, создание, изменение, импорт, работу с
рассмотрениями, дубликатами и справочником причин отказа. `read.all_candidates`
открывает досье организации; без него доступ задаётся назначением на этап интервью
или стажировки. Изменять карточку может ответственный за активное рассмотрение,
а без него — ответственный рекрутер карточки. Доступ к оргструктуре сам по себе
не открывает досье. Замещения ещё не реализованы.

## Защита данных

Реализовано:

- Пароли через bcrypt; минимум 12 символов. Токен сессии содержит 256 бит случайности,
  выдаётся при входе; в БД сохраняется только SHA-256 digest. Срок сессии — 12 часов
  как техническое начальное значение, отдельной бизнес-политики пока нет.
- Выход удаляет сессию. Изменение пароля и активности отзывает все сессии пользователя
  одним DELETE в той же транзакции. Вход и изменения пользователя блокируют его строку,
  чтобы завершившийся сброс пароля не оставлял сессию, созданную по старому паролю.
- Ограничение входа: 10 запросов в минуту на IP. В production счётчик общий через
  Solid Cache; в development/test — память процесса. Для неизвестного логина выполняется
  проверка bcrypt, ответ совпадает с ошибкой пароля.
- API использует Bearer-токен в заголовке, не принимает его в URL.
  Ответы помечены `Cache-Control: no-store`; пароль и токен фильтруются в Rails-логах.
- Аудит записывается в транзакции изменения. В него попадают только явно разрешённые
  поля; новые неизвестные поля автоматически не журналируются.
- PostgreSQL проверяет FK, уникальность логина/назначения, нормализованный формат
  логина, структуру permissions, длину названий, формат digest сессии.
- В production включён HTTPS redirect; `/up` исключён для health check.
- Истёкшие сессии удаляются фоновым заданием пакетами по 1 000 каждый час.

Остаётся для развёртывания (не выполнено автоматически):

- Runtime-подключение к PostgreSQL под отдельной ролью без SUPERUSER/CREATEDB/DDL;
  миграции под владельцем схемы. Для `audit_events` runtime-роли нужны SELECT и INSERT,
  но не UPDATE/DELETE. Сейчас локальная разработка использует пользователя Docker PostgreSQL.
- Шифрование дисков, файлов резюме и резервных копий средствами инфраструктуры,
  резервное копирование вне основного сервера и проверка восстановления.
- Для удалённого PostgreSQL — TLS с проверкой сертификата через настройки подключения.
- Ограничение размеров HTTP-запросов на proxy; настройка доверенных proxy и домена.
- Политика хранения/удаления персональных данных, тестов, переписки и аудита.
- Контроль сохранения последнего активного администратора и процедуры восстановления доступа.

Имена, контакты и резюме не шифруются на уровне приложения. Файлы резюме хранятся
в закрытом Active Storage; шифрование чувствительных полей и файлов требует отдельного
решения при настройке production-хранилища.

## Чтение и запись

- Списки используют пагинацию по `id` (`cursor`, `limit`): 50 строк по умолчанию,
  максимум 200; аудит идёт в обратном порядке. Нет `COUNT(*)` и больших `OFFSET`.
- Пользователи и подразделения фильтруются по `branch_id`; область доступа применяется
  до пагинации. Для запросов филиала добавлены индексы `(branch_id, id)`.
- Список пользователей выбирает только публичные колонки и загружает подразделения
  заранее. Тест проверяет, что количество SELECT не растёт с количеством пользователей.
- Уникальные индексы логина и token_digest обслуживают вход и проверку сессии.
  Индекс `expires_at` обслуживает удаление просроченных сессий.
- Индекс аудита `(subject_type, subject_id, created_at)` предназначен для истории объекта;
  общий список использует PK. Индекс автора позволяет поддерживать FK и будущие фильтры.
- Удалён отдельный индекс назначения по `user_id`: его покрывает уникальный
  `(user_id, department_id)`. Индексы на `active`, весь JSONB и каждую колонку не добавляются.
- Дополнительные уникальные `(id, branch_id)` нужны для составных FK: это сознательная
  стоимость записи ради целостности назначений.
- Для импорта далее использовать ограниченные пакеты и `insert_all`/`upsert_all`
  с ключами источника. Такие операции обходят Rails-валидации и аудит: импорт должен
  явно проверять данные и формировать свой протокол. CRUD сотрудников сохраняет валидации.

### Воспроизводимый локальный замер

Команда: `RAILS_ENV=test bin/rails runner script/benchmark_database.rb`.
Скрипт создаёт 10 000 синтетических пользователей и назначений, проверяет ограничения,
выполняет EXPLAIN ANALYZE, затем откатывает транзакцию. Production запуск запрещён.
Тестовая БД должна быть выделена; не запускать одновременно с тестами.

Результат 17.10.2026 на локальном PostgreSQL:

| Операция | Время | Прочитано строк узлом индекса |
| --- | --- | --- |
| Вставка 10 000 пользователей + 10 000 назначений пакетами по 1 000 | 2 341,18 мс | — |
| Поиск логина | 0,052 мс | 1 |
| Страница из 50 пользователей после 9 000-го через cursor | 0,084 мс | 50 |
| Та же страница через OFFSET 9 000 | 1,991 мс | 9 050 |

Это одиночный синтетический замер, не SLA и не итоговая нагрузочная проверка.
Вставка не включает вычисление bcrypt для каждого сотрудника и сетевые интеграции.
Измерение проводится до отката, без стоимости финального COMMIT.
Для нагрузки 101–1 000 резюме/откликов в день потребуется отдельный профиль:
размер резюме, объём переписки, конкуренция вебхуков, число пользователей и пиковые пачки.

Для внешних событий — уникальность `(provider, external_event_id)`;
для объектов источников — отдельные идентификаторы, не смешанные с внутренними `id`.
Для единственного активного рассмотрения уже действует частичный уникальный индекс
по кандидату. Для бронирований планируется ограничение пересечения
интервалов в PostgreSQL; для оформления — транзакция с блокировкой заявки и уникальным
событием оформления, чтобы не закрыть последнее место дважды.

## Проект переходов и ближайшая работа

1. **Шаблон → заявка → кампания (основа реализована).** Версии и переходы описаны
   в документе API. При явном начале рассмотрения фиксируется актуальная версия условий.
   Кампания: ожидает разрешения → работает → приостановлена; возобновление через рекрутера.
   Заявка: черновик → готова к подбору → в подборе → закрыта;
   пауза/возобновление и отмена отдельными действиями.
2. **Кандидат и рассмотрение (реестр и базовые переходы реализованы).** Первичный диалог → тест → решение рекрутера →
   собеседование → обязательная стажировка, если задана → решение о найме →
   внутренний оффер → оформление. Отказ хранит автора, причину и разрешение следующего предложения.
3. **Импорт и каналы (JSON-импорт реализован).** Образец реальной выгрузки, пробный импорт, сверка файлов;
   проверенные контракты HH/ChatApp, повторы событий и ручной перехват.
4. **ИИ и тесты.** Никаких окончательных решений вместо назначенного сотрудника;
   срок 48 часов, версии и повторная попытка через рекрутера.
5. **Календарь, стажировка, оффер.** Запрет двойной записи, одна повторная запись после
   неявки, заполнение места только оформлением; возврат ровно одного места.
6. **Отчёты и пилот.** Факты переходов и событий, проверка восстановления,
   нагрузка, миграция и пилот на одной кампании.

До реализации зависимых сценариев уточнить: момент фиксации условий и начала рассмотрения,
паузу срока теста/встреч/стажировки, правила баллов и просрочки, сроки напоминаний,
замещения и передачи, продолжительность стажировки, изменение количества мест,
индивидуальные поля оффера, срок давности тестов, возможности интеграций и поставщика ИИ.
Начальные технические настройки доступа и сессий выше не заменяют эти решения.
