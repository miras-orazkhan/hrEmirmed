# Организация разработки субагентами

## Роли

Основной агент — архитектор и ревьюер. Он читает ТЗ, определяет границы этапа,
контракты моделей/API, требования безопасности и критерии приёмки. Затем выдаёт
узкие задачи, проверяет результат и формулирует корректировки. Завершённость
подтверждается интеграционными тестами и просмотром изменений.

Субагенты реализации получают ограниченный список файлов и конкретное поведение.
Для новых ограниченных задач используется `gpt-6-luna`. Агент тестирования получает
отдельное ТЗ и не исправляет производственный код, чтобы проверки оставались
независимыми. Субагенты не меняют чужие файлы и не запускают миграции общей БД.

## Текущий этап: веб-интерфейс и настройки

По прямому запросу пользователя веб-поток реализован на Rails views и Hotwire;
PRODUCT.md и дизайн seed `69c7d062` задали продуктовые ограничения и направление.
Основные рабочие потоки и экраны администрирования уже в коде. Текущая работа —
закрытие найденных дефектов настроек и выравнивание документации с фактом.

| Область | Текущее состояние | Граница |
| --- | --- | --- |
| Основные рабочие потоки | Вход, кандидаты, шаблоны, заявки, кампании, рассмотрения, резюме | Поведение задают существующие сервисы и разрешения |
| Администрирование в UI | Сотрудники, роли, филиалы, подразделения, юрлица, причины отказа | Импорт кандидатов и разрешение дублей — пока только API |
| Обновление реестров | Поиск заменяет `workflow_list`; старт рассмотрения — `_top` | Этап/завершение остаются в `applications_candidate_<id>` |
| Открытые дефекты | Частичный PATCH пользователя, тест пагинации (45 записей при размере 50), nav причин отказа | См. [web_interface.md](web_interface.md) |
| Следующие этапы | Каналы HH/ChatApp, тесты кандидатов, календарь, оффер | Не начинать без отдельного контракта |

## Порядок работы

1. Архитектор фиксирует контракт и область файлов, включая то, что задача не затрагивает.
2. Агент пишет реализацию и сообщает результат локальной статической проверки.
3. Отдельный агент пишет сценарии по внешнему поведению и требованиям ТЗ.
4. Архитектор проверяет код, задаёт конкретные корректировки исполнителю.
5. После завершения зависимых изменений централизованно применяются миграции.
6. Запускаются тесты на общей сборке; дефекты возвращаются ответственному агенту.
7. Результат принимается после успешных проверок и обновления документации.

Проверки ревью: понятные имена, небольшие методы, явные разрешения, фиксированный
порядок блокировок, ограничения БД, отсутствие персональных данных в журнале,
повторяемость импорта, лимиты запросов и загрузок, индексы под реальные запросы.

## Предыдущий этап: API кандидатов

Приняты API карточек/поиска кандидатов, рассмотрений, проверки дублей, JSON-импорта
и приватной загрузки оригиналов резюме.

Исправления того этапа: NULL-семантика CHECK для причины отказа, отзыв доступа после
изменения разрешений, атомарная замена контактов, фильтрация поисковых строк с
персональными данными, пакетное создание предложений дублей и повторная проверка
ответственного после получения блокировок.
