# Импорт кандидатов из прототипа

Первый формат миграции — JSON с устойчивым внешним идентификатором каждой записи. Реальный экспорт прототипа нужно преобразовать в этот контракт после получения образца. CSV/XLSX и перенос исходных файлов этим endpoint пока не поддерживаются.

`POST /api/v1/candidate_imports` требует `import.candidate` и Bearer-сессию. Дополнительное право ручного создания кандидатов не требуется.

```json
{
  "candidate_import": {
    "rows": [
      {
        "external_id": "legacy-candidate-123",
        "full_name": "Иван Иванов",
        "phone": "+77011234567",
        "email": "ivan@example.com",
        "city": "Алматы",
        "preferred_language": "ru",
        "summary": "Опыт работы"
      }
    ]
  }
}
```

Обязательны `external_id` (непустая строка до 200 символов) и `full_name`. Телефон указывается в международном формате с `+`; email нормализуется в нижний регистр. Provider всегда `prototype`. Ответственным и автором становится сотрудник, выполняющий импорт; поля владельца, источников и пути файлов из входных строк игнорируются.

Размер HTTP-тела ограничен 5 МиБ, число строк — от 1 до 1000. Выполнение синхронное; большие выгрузки отправляются отдельными пакетами. На уровне reverse proxy также следует ограничить размер HTTP-тела, чтобы отклонять большие запросы до JSON-разбора Rails.

Ответ `201` содержит `id`, `provider`, `created_by_id`, `created_at`, `total_count`, `imported_count`, `skipped_count`, `rejected_count` и `row_results`. Каждая строка результата содержит `row_number` (нумерация с 1), `status` (`imported`, `skipped`, `rejected`); успешно добавленная строка также содержит `candidate_id`, отклонённая — машинный `code` (`invalid_row`, `invalid_external_id`, `invalid_field_type`, `validation_failed`, `invalid_reference`, `conflict`). Имена, контакты, содержимое ошибочных полей и тексты SQL-ошибок в отчёт не записываются. Невалидная форма пакета возвращает `422`, слишком большое тело — `413`.

Пара `(prototype, external_id)` обеспечивает повторяемость: существующая запись пропускается без изменения её полей. Совпадение имени или контактов не приводит к автоматическому объединению. Разные внешние ID остаются разными кандидатами; возможные дубли разбираются отдельно. Повтор одного ID в пакете и конкурентная загрузка одного источника не создают лишнего кандидата: ошибка уникальности откатывает всю строку. Кандидаты и итоговый отчёт фиксируются одной транзакцией; ошибочная строка откатывается до savepoint, остальные продолжают обрабатываться. Повтор пакета после потери HTTP-ответа безопасен для карточек, но создаёт новый отчёт с пропущенными строками. При взаимной блокировке пересекающихся пакетов БД откатывает один пакет целиком; API возвращает `409 import_conflict` с `retryable: true`, после чего пакет можно повторить.

`GET /api/v1/candidate_imports` возвращает собственные отчёты без подробностей строк, по убыванию ID, с `limit`, `cursor` и `X-Next-Cursor`. `GET /api/v1/candidate_imports/:id` возвращает полный отчёт. Администратор видит все отчёты; обычный сотрудник — только свои, даже при наличии общего доступа к кандидатам. Для обоих запросов требуется `import.candidate`. Отчёты неизменяемы через модель и API. Для списка используется индекс `(created_by_id, id)`; объёмные JSON-результаты не выбираются в запросе списка.

Импорт не открывает рассмотрения, не запускает ИИ и не отправляет сообщения. Исходные резюме загружаются через отдельный защищённый API файлов кандидата после сверки внешних идентификаторов. Пути к локальным файлам или URL из JSON не читаются и не скачиваются.
